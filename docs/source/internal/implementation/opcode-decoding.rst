Opcode Decoding
===============

.. warning::
   **varm is not stable.** This implementation may change without notice.

1. Opcode Decoding Overview
---------------------------

Opcode decoding is the process of extracting the instruction type from a
32-bit encoded instruction. The opcode identifies which operation the VM
should perform (MOV, ADD, LDR, etc.).

In varm, the opcode is an 8-bit value stored in bits [31:24] of each
instruction. This design allows for up to 256 distinct instruction types,
though not all are currently implemented.

Why it matters for performance
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The opcode decode step is on the critical path of every instruction
execution. The current implementation uses O(1) array indexing for
maximum performance. Alternative designs (hash tables, switch statements)
would introduce branch misprediction penalties and cache misses.

2. Bit Extraction
-----------------

Each instruction is decoded using a series of bitwise shift and mask
operations. The instruction format is fixed:

::

   31:24    23:20    19:16    15:12    11:0
   ┌───────┬───────┬───────┬───────┬─────────────┐
   │ Opcode│  Cond │   Rn  │   Rd  │   Operand   │
   │ 8 bit │ 4 bit │ 4 bit │ 4 bit │   12 bit    │
   └───────┴───────┴───────┴───────┴─────────────┘

The bit extraction operations are defined as follows:

.. code-block:: c

   // src/vm/core.c:109-110
   u8 opcode = (instr >> OPCODE_SHIFT) & 0xFF;   // Bits 31:24
   u8 cond   = (instr >> COND_SHIFT) & 0xF;     // Bits 23:20

   // For operand decoding (see operand-decoding.rst)
   u8 rn     = (instr >> RN_SHIFT) & 0xF;       // Bits 19:16
   u8 rd     = (instr >> RD_SHIFT) & 0xF;       // Bits 15:12
   u32 operand = instr & OPERAND_MASK;           // Bits 11:0

The shift constants are defined in ``include/vm.h``:

- ``OPCODE_SHIFT`` = 24
- ``COND_SHIFT`` = 20
- ``RN_SHIFT`` = 16
- ``RD_SHIFT`` = 12
- ``OPERAND_MASK`` = 0xFFF

3. Lookup Table Design
----------------------

varm uses a function pointer array for O(1) instruction dispatch:

::

   typedef void (*exec_fn)(vm_state_t*, u32);

   static exec_fn exec_table[256] = {0};  // NULL-initialized

   // During initialization:
   exec_table[OP_MOV] = exec_mov;
   exec_table[OP_ADD] = exec_add;
   // ... etc

The table is indexed directly by the 8-bit opcode value, eliminating
branch prediction overhead. Unimplemented opcodes remain as NULL entries.

Generated at build time
~~~~~~~~~~~~~~~~~~~~~~~

The instruction name to opcode mapping is generated by
``scripts/gen_lookup_tables.py`` at build time. This script:

1. Parses ``include/opcode.h`` for opcode definitions
2. Generates ``src/asm/generated/instr_name_lookup.c``
3. Uses FNV-1a hash for instruction name lookup

4. Implementation
-----------------

The execution table is initialized once during ``vm_run()``:

.. code-block:: c

   static exec_fn exec_table[256] = {0};

   static void
   init_exec_table(void)
   {
       exec_table[OP_MOV]  = exec_mov;
       exec_table[OP_MVN]  = exec_mvn;
       exec_table[OP_ADD]  = exec_add;

Dispatch in vm_step()
~~~~~~~~~~~~~~~~~~~~~

The instruction fetch and dispatch occurs in ``vm_step()``:

.. code-block:: c

   // src/vm/core.c:101-124
   void
   vm_step(vm_state_t* vm)
   {
       u32 pc = vm->regs.pc;
       u32 instr = vm_mem_read32(vm, pc);

       u8 opcode = (instr >> OPCODE_SHIFT) & 0xFF;
       u8 cond   = (instr >> COND_SHIFT) & 0xF;

       vm->regs.pc += 4;

       if (check_condition(vm, cond)) {
           if (exec_table[opcode] != NULL) {
               exec_table[opcode](vm, instr);
           } else {
               printf("Unknown opcode: 0x%02X\n", opcode);
               vm->running = 0;
           }
       }
   }

Handle unknown opcodes
~~~~~~~~~~~~~~~~~~~~~~

When an unimplemented opcode is encountered:

1. The NULL entry is detected
2. An error message prints the opcode value
3. ``vm->running`` is set to 0, halting execution

This graceful degradation allows debugging of partial implementations.

5. Complexity Analysis
----------------------

+-------------------+------------+----------------------------------+
| Operation         | Complexity | Notes                            |
+-------------------+------------+----------------------------------+
| Bit extraction    | O(1)       | 5 shift/mask operations          |
| Array lookup      | O(1)       | Single memory access             |
| Function call     | O(1)       | Indirect call via function ptr   |
| Total per instr   | O(1)       | Dominated by instruction exec    |
+-------------------+------------+----------------------------------+

The decode phase adds approximately 5-10 CPU cycles per instruction,
negligible compared to memory operations or multiplication.
